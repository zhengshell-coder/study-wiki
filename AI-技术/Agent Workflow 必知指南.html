1.1 · 是什么LLM 是被动回答者，Agent 是主动行动者——一个公式看懂所有 Agent 产品。
Agent = LLM + 上下文 + 工具 ＝ 大脑 + 眼睛 + 手脚；生产级再加 Harness
大脑 · LLM 决策内核+ 眼睛 · 上下文（每次决策能看到的全部信息）+ 手脚 · 工具（能改变世界的全部手段）= Harness · 约束 + 验证 + 纠正
维度LLM（被动回答者）Agent（主动行动者）
发起方式人问一句，答一句人给目标，自己拆解、排程、执行
与世界的连接只输出文本调用工具，读取并改变世界
过程控制单轮或少数几轮对话ReAct 循环：思考 → 行动 → 观察 → 再思考
纠错方式靠人追问纠正观察结果、反思、自我修正
产物一个答案一份任务结果（代码、报告、操作记录）
信任成本说错话的成本做错事的成本——所以生产级必须加 Harness
A

定义：具备自主闭环能力的智能主体

感知 → 规划 → 决策 → 执行 → 反馈迭代
理解高层次目标、独立拆解为可执行子任务、动态调用外部工具与资源，并在执行中持续反思修正，直至完成复杂目标。
业界标准口径：Workflow 与 Agent 同属"Agentic 系统
Anthropic 的划分：Workflow = LLM 与工具按代码预定义的路径编排；Agent = LLM 自己动态决定流程与工具调用。区别不在"用没用大模型"，而在路径由谁决定——这也是本指南的核心标尺（1.3）。
B

从 Demo 到生产：Harness 公式

Demo = LLM + 工具；生产 = Demo + 约束 + 验证 + 纠正
约束防越界、验证发现错误、纠正恢复异常——生产级 Agent 的代码大头在后三者，而非工具本身。
模型负责"能做事"，Harness 负责"可靠地做事"
第 5.2 节的职责三分与第 6.3 节的确定性引擎，都是这句话的展开。
Harness 要随模型"做减法"
Anthropic 2026 长程应用 Harness 实践：每个 Harness 组件都编码了一个"模型做不到什么"的假设——模型升级后要重新验证，过时的脚手架应当删掉。
记住这句：模型负责"能做事"，Harness 负责"可靠地做事"——评估任何 Agent 产品，先看它的 Harness 有多厚。
蒸馏自《Agent 概念与技术发展深度解析》01 引言、02 基础架构、06 Harness；Anthropic《Building Effective Agents》亦持相同立场。
1.2 · 是什么Agent 运行时没有魔法——只是一个不断向消息列表末尾追加内容的循环。
ReAct Loop · 想 → 做 → 看，循环直至交付（节点按序点亮）
A

跑起来就是一个 ReAct 循环

想 → 做 → 看，不断向轨迹末尾追加
模型思考该做什么、调用工具行动、观察返回结果再想下一步，直至交付。
现代写法：收集上下文 → 行动 → 验证 → 重复
ReAct 是学术起点；今天的生产实现是原生 tool calling 循环（模型返回工具调用 → 执行 → 结果追加 → 再调模型）。Claude Agent SDK 把它总结为四步，并强调"验证"是一等步骤：规则校验、跑测试、截图自检或另设评审模型。
越简单越可靠
警惕不必要的复杂度——多数"Agent 框架"的价值不在循环本身，而在循环之外的工程。
B

上下文 = 静态前缀 + 动态轨迹

系统提示词与工具定义是静态前缀
用户消息、模型回复、工具结果是只增不减的轨迹——这解释了成本与压缩的由来。
推论：轨迹只增不减，成本与"腐烂"随之而来
压缩、隔离、切片都是为此而生——第 6.2 节的切片设计正是这一推论的工作流化解法。
上下文是 Agent 唯一能看到的世界——管好上下文，就管好了 Agent 的一半（1.4 把"管好"拆成可执行的五板斧）。
蒸馏自《Agent 概念与技术发展深度解析》02 基础架构。
1.3 · 是什么不是"要不要 Agent"，而是"把多少决策权交给模型"——这是一条光谱。
Autonomy Spectrum · 点击任一格：决策权从左到右逐格移交
← 人定路径 · 可预测 · 好审计决策权归属模型定路径 · 自适应 · 要护栏 →
另一条轴：单 Agent ↔ 多 Agent　多 Agent 不是光谱上"更自主"的一格，而是与自主程度正交的拓扑选择：一条固定工作流可以串起多个 Agent，一个高度自主的 Agent 也可以单打独斗。先决定"路径由谁定"（本光谱），再决定"拆不拆、怎么拆"（1.5）。

提示词链
Prompt Chaining
何时用任务能干净地分解为固定子步骤——用延迟换每一步的准确率。
例子大纲 → 写作 → 校对；先抽取结构化信息再生成。
要点步骤之间加检查门，失败早停——把一个大提示词拆成一条链，是最常用的第一步。
路由
Routing
何时用输入可分为几类，各类适用不同处理——关注点分离，各分支独立优化。
例子工单分类进专家分支；简单问题走小模型、难题走大模型。
要点也常用于成本路由：让大部分流量走便宜的那条路。
并行化
Parallelization · Sectioning / Voting
何时用子任务相互独立（分段提速），或需要多视角交叉验证（投票增信）。
例子多份审计并发跑（Sectioning）；多个模型实例对同一输出投票（Voting）；护栏与正文分头处理。
要点6.2 的"审计 ×N"就是 Sectioning 的生产化形态——快，但 token 成本随并发线性增长。
编排者-执行者
Orchestrator-Workers
何时用子步骤无法预知——例如要改哪些文件、改什么，取决于任务本身。
例子编码任务由编排者按输入动态拆分，工作者各自完成，再汇总。
要点与"多 Agent 协作"同源，但控制点是一个中心模型；Workgroup（5.4）就是它的团队工程化。
评审-优化
Evaluator-Optimizer
何时用有明确的评价标准，且逐轮迭代能带来可度量的提升。
例子生成 ⇄ 评审循环；文学翻译的逐轮打磨；多轮检索式深度调研。
要点一轮就是一次全价调用，必须设最大轮次——Code→Audit→Fix（5.3）正是它落在编码域的形态。
自主 Agent
Autonomous Agent
何时用任务开放、路径不可预知，但反馈可验证（测试、环境状态）。
例子跑测试的编码 Agent；看屏操作的 computer use。
要点光谱最右端：自治越大、爆炸半径越大——护栏分级与预算上限必配（3.2）。
A

路径可写死用工作流，不可预知才放开自主

工作流保可预测，自主换适应性
路径固定时用工作流，控制流写在代码里、可测试；只有路径不可预知时，才把决策权交给模型；多数生产系统混合使用。
原则：从简单到复杂
先优化提示词，再考虑工作流，最后才引入自主——OpenAI 指南补充：单代理先靠加工具扩能力，多代理只在确有必要时引入；能用一次调用解决，就不要任何编排。
工具设计 = Agent 的"人机界面"（ACI）
Anthropic：花在工具定义上的心思应不少于提示词——名称不重叠、参数防呆、返回高信号内容；工具集合要用真实任务评估、让 Agent 参与改写。
B

术语对齐：五个高频词

工具 Tools
模型可调用的函数——读文件、跑命令、查接口，是改变世界的手段。
技能 Skills
打包的领域知识与操作流程，按需加载，让通用 Agent 变成领域熟手。
MCP
工具与数据源接入的开放协议，已成事实标准——一次接入，处处可用。
Harness
模型之外的一切：循环、工具、上下文管理、权限、验证与恢复——"Agent = 模型 + Harness"。
子 Agent
在独立上下文中执行子任务、只回传结论，让主上下文保持干净。
这条光谱是全文的统一标尺：第 3 章的失败是"放错了格子"，第 5、6 章的设计是"把决策权放在正确的格子"。
蒸馏自《Agent 概念与技术发展深度解析》02、11；光谱与上方模式库取自 Anthropic《Building Effective Agents》（五种工作流模式 + Agent），并参照 OpenAI《A Practical Guide to Building Agents》的"单代理优先"原则与 Azure 架构中心的三级复杂度分层。
1.4 · 是什么上下文不是越大越好——它是一份有限的注意力预算：窗口里要么是高信号，要么是正在腐烂的噪音。
Attention Budget · 注意力预算与 Context Rot（Anthropic，Claude Code 团队口径）
① 裁剪

先做减法

工具清单最小化、输出高密度化
工具不重叠、描述清晰；可重新获取的旧工具结果直接清除——最便宜的杠杆，且无损。
工具按需加载 · 用代码调工具
工具多时先"搜"再加载定义（Tool Search）；让 Agent 写代码批量调用 MCP 工具，中间结果不进窗口——Anthropic 案例 token 从约 15 万降到约 2 千。
② 卸载

外存当内存用

文件系统是无限外存
50K token 的网页 → 500 token 摘要 + 可回溯指针（Manus 实践，约 100:1）；状态写进 todo.md / scratchpad。
关键是可逆
压缩掉的原文随时可取回——激进剪裁不可逆，才是事故源头。
③ 隔离

子代理挡噪音

噪音大的子任务交给子代理
独立窗口消化，只回传 1–2K token 摘要（Anthropic 实践）；其多代理调研系统比单代理高出约 90%，但 token 消耗约为聊天的 15 倍——值不值要算账。
团队侧落点
6.2 的"审计 ×N 切片"就是隔离的工程化。
④ 压缩

近满则摘要重启

把旧对话摘要成"重启点"
Anthropic 公布：上下文编辑在 100 轮检索任务中让 token 消耗下降 84%，配合记忆工具任务表现提升 39%；压缩水位线常设在窗口 70–95%。
难在取舍
压太狠会丢掉后文才需要的细节——摘要质量即压缩质量。
⑤ 缓存 · 检索

便宜的先便宜

静态前缀走提示缓存
Agent 的系统提示恒定不变，缓存命中部分费用约省 90%。
知识按需检索
RAG 是上下文工程的子集：检索管"知识进来"，上下文工程管"整个窗口的一生"。
⑥ 顺序

从最便宜的杠杆开始

精简工具 → 清除旧结果 → 压缩 → 记忆 → 子代理
每加一层复杂度，都要有对应收益证明——上下文工程同样遵循"从简单到复杂"。
A

跨会话：记忆与结构化笔记

记忆工具：笔记写到 /memories，按需读回
跨会话持久化——5.5 的记忆飞轮就是它的团队受治理版。
结构化笔记让推理活过压缩
把计划与状态写进文件，窗口重启后仍可续命——Claude 连玩数千步宝可梦靠的就是这招。
B

会话 ≠ 上下文窗口

把"看什么"从窗口移到 Harness
Anthropic Managed Agents：会话日志作为窗口外的上下文对象，按位置切片取回（getEvents），要什么取什么。
顺带治好"上下文焦虑"
模型感知临近上限时会提前草草收工——解法不在提示词，而在重置与预算的工程设计。
提示词工程优化一条指令，上下文工程优化 Agent 的一生——窗口里每一个 token 都要挣到自己的位置。切片（6.2）与记忆（5.5）都是这门学科在团队侧的落点。

1.5 · 是什么拆成多个 Agent 的第一动因不是"更像团队"，而是注意力管理——每个上下文只装它该装的东西。
Collaboration Topologies · 五种协作拓扑（点击切换，综合 LangGraph / OpenAI / Azure 口径）
主从式（主管-工作者）
Supervisor / Worker
何时用子任务可并行、可拆解，编排者只需汇总——最常用、最好控的默认拓扑。
例子编排者-执行者模式（1.3）；并发审计 ×N（6.2）；Opus 主控 + Sonnet 子代理。
风险编排者是单点：拆解质量决定上限，且自身上下文必须保持干净。
移交式
Handoff
何时用对的专家要在处理过程中才浮现——先接单，干不了再转交。
例子客服： frontline 接待 → 退款专家接手；OpenAI Agents SDK 的原生 handoff 原语。
风险无限移交环（A→B→C→A）；路由路径不可预测，难审计——要设移交次数上限。
分层式
Hierarchical
何时用任务规模大到单一编排者管不过来，需要分组治理。
例子跨部门协作模拟：总编排者拆域，各组编排者再拆给工作者。
风险每层都是信息瓶颈与错误放大器——层数是风险乘数，能两层就别三层。
对等式
Peer-to-Peer
何时用各方平等协商、无天然中心——跨团队、跨组织的 Agent 协作愿景。
例子A2A 协议（Linux Foundation）下的跨厂商 Agent 互委托。
风险协调最难：对话循环、死锁、无人负责——生产系统慎用，需协议级约束。
群聊式
Group Chat
何时用需要头脑风暴、多轮互评（maker-checker）达成共识。
例子方案评审会：生成者提案、批评者挑刺、仲裁者定稿。
风险对话循环、难以收敛；必须有主持人控序与明确的停止条件。
A

为什么拆：四个正经理由

① 上下文隔离——第一动因
大噪音子任务（全库检索、网页抓取）交给子代理消化，主上下文只收 1–2K token 结论。
② 并行加速
独立子任务并发执行：审计 ×N、多视角投票（1.3 并行化）。
③ 专业化
每个 Agent 的提示词、工具集、技能各自最优——胜过一个什么都会一点的大杂烩提示词。
④ 安全边界
不同信任级别配不同权限：只读审计者与可写编码者天然分区。
B

什么时候不该拆

单 Agent + 工具，往往是企业场景的默认正解
Azure 架构中心明示：提示词复杂到管不过来、工具多到过载、或确需安全隔离，才值得引入多 Agent。
业界共识的分界线：读多写少才拆
Anthropic（多代理调研）与 Cognition（《Don't Build Multi-Agents》）看似对立，其实结论一致：广度优先、可并行的"读"任务（调研、审计）适合拆；强耦合的"写"任务（改同一份代码）拆开会因隐含决策冲突而出错，宜单线程共享完整上下文。
协调开销是真实的
每次交接都是一次信息损耗与验证成本——拆得越碎，损耗越大。
级联错误
每一层都可能放大上一层的错误；层数是风险乘数，不是能力加成。
C

通信：协议与共享状态

A2A：跨厂商互操作标准
Linux Foundation 托管——能力发现、任务委托、状态回传，不绑定任何一家框架。
共享上下文层
跨 Agent 的持久状态外置：同一份业务定义、同一份治理策略，一次维护、全员继承。
交接验证门
每次交接过结构化 schema 校验；回传摘要控制在 1–2K token——既省注意力，又防信息失真。
D

编排者的自我修养

只拆解、派发、汇总，不亲自干活
编排者上下文必须最干净——它一旦被噪音污染，整个系统跟着失焦。
失败要向上冒泡
子代理不自行其是：失败、超时、超预算一律上报，由编排层决定重试还是升级人审。

那正是这套架构一开始就要避免的"上层大模型调度"陷阱。
进程与工作区隔离保底
每个任务拥有独立工作区与配置目录，同一仓库的多任务互不干扰；所有产物持久化入库。

业界做法：Agent 间交接按结构化 schema 校验、失败即重试或降级——多 Agent 生产失败的头号原因不是模式选错，而是上下文不一致；共享、受治理的上下文层要在部署前就位。
Harness 视角：契约只是第一层
约束防越界、验证发现错误、纠正恢复异常；生产级 Agent 的代码大头在后三者，而非工具本身。
持久

持久执行：长任务不怕中断

事件溯源日志：先落盘，再执行
每一步状态变更写入持久日志（Write-Ahead Log 思路）——进程崩了、断电了，状态还在。
确定性重放 = 断点续跑
故障后从最后一个一致事件恢复重跑，而不是从头再来——小时级长任务的生死线。
同款思路的工业级实现
Temporal、Restate、LangGraph checkpointing、微软 Agent Framework 的 checkpoint 与 time-travel——持久执行已是工作流引擎的标配。
谱系：从 BPM 到 Agentic Workflow
Petri 网 / BPMN → 工作流引擎 → RPA → AI 节点化——确定性内核一脉相承，变的是节点里的"工人"。
时光机

时间旅行调试

回退到任意历史状态重跑
检查点 + 重放：定位"从哪一步开始走偏"，而不是对着最终失败结果猜。
主流框架均已内建
LangGraph 原生提供 checkpoint 与 time travel（回到任意步骤改状态重跑）；微软 Agent Framework 工作流提供 checkpoint、streaming 与 human-in-the-loop。
与 3.2 轨迹留痕同源
轨迹既是可观测的资产，也是可调试的素材——留痕做扎实了，时间旅行才有可能。
幂等

幂等、重试与补偿

节点幂等：重试安全的前提
同一输入重跑，副作用只发生一次——写操作用幂等键、外部调用带去重。
重试要有退避与上限
指数退避 + 最大次数，超限升级人审——与 3.2 的护栏分级同一哲学。
长流程用 Saga 补偿
跨系统流程无法原子提交：每步预定义回滚动作，失败逆序补偿，而不是半途而废。
版本

定义即代码：版本化与迁移

工作流定义像 API 一样版本化
变更可评审、可灰度、可回滚——"流程是工程资产"的最后一道证明。
在途实例迁移是引擎级难题
通行做法：旧版本实例跑完、新版本只接新任务——升级不断流。
代码 / YAML 双形态
代码态利于测试与复用，声明态利于评审与共享；能导入导出，团队才能复用彼此的流程。
把不可控的自然语言输出，收束到可控、结构化、确定性的接口契约——引擎从此可以确定性调度。记住边界：Git 隔离保的是任务状态与合并语义，不是操作系统级沙箱。
来源：契约边界参考 agent-workflow 设计随笔（XML 信封）与业界结构化输出实践；持久执行、时间旅行、幂等与 Saga 参照 Temporal / Restate / LangGraph / Microsoft Agent Framework 公开文档；Git 隔离非 OS 沙箱以该仓库 README"Platform and safety"为准。

架构是连续的，演进才不需要重写——这是路线图中最有价值的一个判断；也呼应 4.1：模型变强会让决策权右移，连续的架构才接得住。

6.5 · 边界与行动把全篇收成两张卡：什么不该做（边界），第一步做什么（行动）。
边界

三句话划清安全与适用边界

Git 隔离 ≠ 操作系统沙箱
子进程拥有 daemon 账号的文件与网络权限，只运行可信的 Agent、技能与 MCP 定义。
不是所有任务都值得上工作流
单次调用能解决就别上工作流；路径固定用工作流；只有路径不可预知才上自主与 Workgroup——回到 1.3 的光谱定位。
自治越大，越要收紧最小权限
与 2.3 的安全边界呼应：审批关口、预算上限、可回滚，是放权的前提。
提示注入是第一大攻击面
系统提示、网页内容、工具返回都可能夹带指令（OWASP LLM01）；多层防御：工具白名单、外部内容只作数据不作指令、出网最小化、高危动作人工审批。
行动

落地行动清单：六件事

① 选一个高频、路径固定的流程，先跑最小闭环
从简单到复杂，先在编码域跑通 Code→Audit→Fix（5.3）。
② 先建评估集，再谈优化
没有评估的优化是凭感觉（3.2）；失败案例回流评估集。
③ 轨迹、决策、反问全量入库
先可审计，再谈智能（3.1）；留痕是规模化的前提。
④ 记忆先审批后注入，管"忘"与"冲突"
飞轮要转，但不能乱转（5.5）。
⑤ 按本地 → 团队 → 云端规划演进
架构从第一天为云端预留，避免推倒重来（6.4）。
⑥ 给每个节点设上下文与预算上限
工具最小化、子代理隔离、压缩水位线与 token 预算（1.4）；超限升级人审，而不是硬试（3.2 护栏）。
从"人带着流程、把 AI 当工具"，到"工作流编排 AI 与人协同"——四个问题看完，剩下的是行动。
