1.1 · 是什么LLM 是被动回答者，Agent 是主动行动者——一个公式看懂所有 Agent 产品。
Agent = LLM + 上下文 + 工具 ＝ 大脑 + 眼睛 + 手脚；生产级再加 Harness
大脑 · LLM 决策内核+ 眼睛 · 上下文（每次决策能看到的全部信息）+ 手脚 · 工具（能改变世界的全部手段）= Harness · 约束 + 验证 + 纠正
维度LLM（被动回答者）Agent（主动行动者）
发起方式人问一句，答一句人给目标，自己拆解、排程、执行
与世界的连接只输出文本调用工具，读取并改变世界
过程控制单轮或少数几轮对话ReAct 循环：思考 → 行动 → 观察 → 再思考
纠错方式靠人追问纠正观察结果、反思、自我修正
产物一个答案一份任务结果（代码、报告、操作记录）
信任成本说错话的成本做错事的成本——所以生产级必须加 Harness
A

定义：具备自主闭环能力的智能主体

感知 → 规划 → 决策 → 执行 → 反馈迭代
理解高层次目标、独立拆解为可执行子任务、动态调用外部工具与资源，并在执行中持续反思修正，直至完成复杂目标。
B

从 Demo 到生产：Harness 公式

Demo = LLM + 工具；生产 = Demo + 约束 + 验证 + 纠正
约束防越界、验证发现错误、纠正恢复异常——生产级 Agent 的代码大头在后三者，而非工具本身。
模型负责"能做事"，Harness 负责"可靠地做事"
第 5.2 节的职责三分与第 6.3 节的确定性引擎，都是这句话的展开。
记住这句：模型负责"能做事"，Harness 负责"可靠地做事"——评估任何 Agent 产品，先看它的 Harness 有多厚。
蒸馏自《Agent 概念与技术发展深度解析》01 引言、02 基础架构、06 Harness；Anthropic《Building Effective Agents》亦持相同立场。
1.2 · 是什么Agent 运行时没有魔法——只是一个不断向消息列表末尾追加内容的循环。
ReAct Loop · 想 → 做 → 看，直至交付
思考 · 该做什么› 行动 · 调用工具› 观察 · 读取返回⟲ 再思考 …… 直至交付
A

跑起来就是一个 ReAct 循环

想 → 做 → 看，不断向轨迹末尾追加
模型思考该做什么、调用工具行动、观察返回结果再想下一步，直至交付。
越简单越可靠
警惕不必要的复杂度——多数"Agent 框架"的价值不在循环本身，而在循环之外的工程。
B

上下文 = 静态前缀 + 动态轨迹

系统提示词与工具定义是静态前缀
用户消息、模型回复、工具结果是只增不减的轨迹——这解释了成本与压缩的由来。
推论：轨迹只增不减，成本与"腐烂"随之而来
压缩、隔离、切片都是为此而生——第 6.2 节的切片设计正是这一推论的工作流化解法。
上下文是 Agent 唯一能看到的世界——管好上下文，就管好了 Agent 的一半。
蒸馏自《Agent 概念与技术发展深度解析》02 基础架构。
1.3 · 是什么不是"要不要 Agent"，而是"把多少决策权交给模型"——这是一条光谱。
Autonomy Spectrum · 决策权从左到右逐格移交
单次调用› 提示词链 / 路由› 工作流 · 路径预定义› 自主 Agent · 模型定路径› 多 Agent 协作
A

路径可写死用工作流，不可预知才放开自主

工作流保可预测，自主换适应性
路径固定时用工作流，控制流写在代码里、可测试；只有路径不可预知时，才把决策权交给模型；多数生产系统混合使用。
原则：从简单到复杂
先优化提示词，再考虑工作流，最后才引入自主——这是控制成本与风险最实用的顺序。
B

术语对齐：四个高频词

工具 Tools
模型可调用的函数——读文件、跑命令、查接口，是改变世界的手段。
技能 Skills
打包的领域知识与操作流程，按需加载，让通用 Agent 变成领域熟手。
MCP
工具与数据源接入的开放协议，已成事实标准——一次接入，处处可用。
子 Agent
在独立上下文中执行子任务、只回传结论，让主上下文保持干净。
这条光谱是全文的统一标尺：第 3 章的失败是"放错了格子"，第 5、6 章的设计是"把决策权放在正确的格子"。
蒸馏自《Agent 概念与技术发展深度解析》02、11；Anthropic《Building Effective Agents》的工作流/Agent 区分。

A

选赛道比选模型更能决定首期成败

成熟赛道吃的是"确定性红利"
编码与调研的任务边界清晰、结果可验证，Agent 容易跑出正循环。

落后赛道等的是"可靠性拐点"

GUI 与企业流程卡在长尾可靠性上
不是"能不能做一次"，而是"能不能连续做一百次不出错"——见 2.2 的 pass^k 读数。
"能做什么"的版图不是均匀的——先选对赛道，再谈投入。
蒸馏自《Agent 概念与技术发展深度解析》12–15 应用篇、18 中美对比。

读数二：看稳定性

2.3 · 能做什么知道 Agent 在哪里会摔，比知道它能做什么更重要——四类典型失败模式。
①

幻觉与静默失败

错了不报错，错误结论流入下游连环污染
对策：验证层 + 关键节点人工复核——见 5.4、6.3。
②

上下文腐烂与"躺平"

轨迹变长、任务变枯燥，推理质量自然衰减
表现为只挑显眼几条认真处理、其余草草收尾。对策：切片与独立上下文——见 6.2。
③

长程一致性：连乘衰减

多步任务成功率是逐步连乘：单步 99%，50 步只剩约 60%
对策：确定性引擎 + 收敛循环，把"走偏"挡在节点之间——见 5.3、6.3。
④

安全与权限：爆炸半径

提示注入、越权工具调用——自治越大，爆炸半径越大
对策：最小权限 + 隔离 + 审批关口——见 6.5。
这些失败模式不是"模型不行"，而是系统设计问题——第 5、6 章的团队方案逐一给出工程对策。
蒸馏自《Agent 概念与技术发展深度解析》02、04、06；Anthropic 关于长程 Agent harness 的公开实践。

3.3 · 实践现状五个痛点指向同一根因：把 AI 当工具分发，AI 就永远只是某个人在某一刻按下的加速键。
维度工具思维（现状）工作流思维（目标）
① AI 的角色工具栏上的按钮：人决定何时调用，结果归调用者所有工作流上的节点：被编排、被触发、被记录
② 过程留痕会话关闭即消失，产出不可审计事件、决策、反问全量结构化入库
③ 知识去向困在个体电脑与聊天记录里提炼为团队记忆资产，按需召回注入
④ 流程归属流程为人制定，AI 被塞进某一格流程是可执行引擎，AI 与人都被它编排
效率上限被单点工具的强弱锁死取决于协作流程的编排能力
A

放任痛点不管，会碎裂成环境治理难题

几百套互不一致的"个人 AI 工作站"
Agent、提示词、模型选型、API Key、技能各人一套，治理无从谈起。
支持侧只能停留在单点救火
没有问题全景，就做不了根因治理与系统级优化。
B

效率上限被流程本身锁死

决定团队效率的是协作流程的编排
AI 工具用得再好，流程不变，效率天花板就不变。
打补丁修不出新形态
加日志、加监控、加报表，都是在已经走偏的产品形态上打补丁。
AI 应该是工作流上的节点，而不该是工具栏上的按钮。这是全篇的支点——第 5、6 章看它如何落成团队方案。
来源：设计随笔上篇第一节、第二节；痛点归纳为作者调研总结。
4.1 · 模型公司方向后训练的重心正从"对齐聊天"转向"训练主体性"——让模型学会做事，而不只是回答。
A

Agentic 后训练：在真实工具环境中用结果奖励

从 RLHF 到 Agentic RL / RLVR
让模型在真实工具环境里跑完整任务，以任务结果为奖励信号——模型被训练得会规划、会调用、会从失败恢复。
各家主线一致
Claude、OpenAI o 系、DeepSeek、Kimi 等，都把 agentic 能力（工具使用、长程任务）作为后训练的主线方向。
B

长程推理：任务时间尺度被拉长

test-time compute 从秒级问答到小时级任务
推理预算换任务长度——"能连续做多长的活"成为新的能力坐标。
METR 时间尺度研究
模型可独立完成的任务长度约每 7 个月翻一倍——若趋势延续，"周级任务"并非遥不可及。
C

对团队的含义：决策权会随模型变强持续右移

模型每强一档，"该交给模型的决策权"就往光谱右移一格
今天写死的路径，明天可能就该交给模型——架构要为右移预留空间（光谱见 1.3，演进见 6.4）。

提示词写得再好，也覆盖不了开发者自己都没意识到要交代的信息——反问的本质，是 AI 帮我们拓展了问题空间。

6.3 · 关键设计引擎必须是确定性的，只有节点内部允许非确定——这是整套架构最关键的一次划分。
图证

契约将非确定性输出收束到端口

Determinism Boundary · 确定性边界
工作流引擎 · 确定性
端口路由 · 重试 · 恢复 · 合并回退——只面对结构化数据
▲ 引擎只面对确定性
接口契约 · XML 信封
Agent 按声明的端口输出结构化信封，框架按名称分发给下游
▲ 输出被契约收束
Agent 推理 · 非确定性
每个 Agent 以独立子进程专注处理自己的任务，输出被约束在契约之内
逐层

契约层：不可控输出 → 可控接口
框架自动注入协议说明，并取标准输出中最后一段完整信封作为有效输出。
否则只能靠上层大模型阅读自然语言、人工搬运
那正是这套架构一开始就要避免的"上层大模型调度"陷阱。
进程与工作区隔离保底
每个任务拥有独立工作区与配置目录，同一仓库的多任务互不干扰；所有产物持久化入库。
Harness 视角：契约只是第一层
约束防越界、验证发现错误、纠正恢复异常；生产级 Agent 的代码大头在后三者，而非工具本身。
把不可控的自然语言输出，收束到可控、结构化、确定性的接口契约——引擎从此可以确定性调度。记住边界：Git 隔离保的是任务状态与合并语义，不是操作系统级沙箱。

6.5 · 边界与行动把全篇收成两张卡：什么不该做（边界），第一步做什么（行动）。
边界

三句话划清安全与适用边界

Git 隔离 ≠ 操作系统沙箱
子进程拥有 daemon 账号的文件与网络权限，只运行可信的 Agent、技能与 MCP 定义。
不是所有任务都值得上工作流
单次调用能解决就别上工作流；路径固定用工作流；只有路径不可预知才上自主与 Workgroup——回到 1.3 的光谱定位。
自治越大，越要收紧最小权限
与 2.3 的安全边界呼应：审批关口、预算上限、可回滚，是放权的前提。
行动

落地行动清单：五件事

① 选一个高频、路径固定的流程，先跑最小闭环
从简单到复杂，先在编码域跑通 Code→Audit→Fix（5.3）。
② 先建评估集，再谈优化
没有评估的优化是凭感觉（3.2）；失败案例回流评估集。
③ 轨迹、决策、反问全量入库
先可审计，再谈智能（3.1）；留痕是规模化的前提。
④ 记忆先审批后注入，管"忘"与"冲突"
