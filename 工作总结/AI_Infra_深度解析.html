什么是 AI Infra

AI Infra（人工智能基础设施）是支撑大模型从训练、微调到推理部署全生命周期的工程化技术栈。如果把大模型比作「发动机」，那么 AI Infra 就是整台「汽车」--底盘、传动系统、燃油供给、散热和仪表盘。没有 Infra，再强的模型算法也无法转化为可规模化交付的服务。

行业焦点已从「模型能力突破」迁移到「工程效率竞争」。DeepSeek-V3 的训练成本仅为 GPT-4 的约 1/20，核心优势并非算法颠覆，而是 AI Infra 层的极致优化--从 MoE 路由到 FP8 混合精度，从通信压缩到流水线调度。这标志着行业进入「Infra 即竞争力」阶段。来源：DeepSeek-V3 Technical Report (2024), SemiAnalysis 训练成本分析

关键组成要素

算力硬件GPU 是核心但非全部。算力增速（H100 vs A100 约 3x）远超互联带宽增速（InfiniBand 200G->400G 仅 2x）。来源：NVIDIA H100/A100 Datasheet

并行存储全闪存并行文件系统（WekaFS、Lustre）支撑 TB 级 Checkpoint 高速读写。

调度系统GPU 拓扑感知调度--将通信密集的任务放在同一 NVLink Domain（同一物理节点内的 8 张 GPU）内。

可观测性GPU 级 Telemetry（SM 占用率、HBM 带宽、PCIe 吞吐、温度）是诊断「算力黑洞」的基础。

关键概念区分：MFU vs HFU
MFU（Model FLOPs Utilization） = 实际计算量 / 模型理论前向+反向 FLOPs。衡量「模型算法层面的计算效率」
HFU（Hardware FLOPs Utilization） = 实际计算量 / 硬件峰值 FLOPs。衡量「硬件层面的计算效率」

两者差异来源：ZeRO-3 / PP 会引入额外通信-计算重叠，导致 HFU > MFU。例如某训练任务 MFU = 42% 但 HFU = 52%。本文中「35-45% 利用率」指 MFU。来源：Megatron-LM (NVIDIA, 2022)；DeepSpeed ZeRO (Microsoft, 2019-2023)
洞察：AI Infra 不是「买卡就行」的硬件采购问题，而是一个跨五层技术栈的系统工程。花 10 亿美元建的集群，如果 Infra 工程能力不到位，有效算力可能只有理论峰值的 30-40%。

在进入具体技术分析之前，需要先理解一个关键区分：训练侧 Infra 和推理侧 Infra 是两个截然不同的工程世界（见上方对比表）。后续章节将分别从这两个维度展开。
GPU「又忙又闲」困局
花 2000 亿建的集群，一半算力在「等待」中被浪费--五大根因与优先级排序

现象描述：一个价值百亿的悖论

2024-2025 年，全球头部厂商累计部署超 200 万张 H100/H200 级别 GPU。仅微软、Meta、Google、亚马逊四家，2024 年 AI 资本支出合计超 2000 亿美元。然而，集群平均 MFU 仅 35-45%，推理集群 SM 占用率在 15%-95% 间剧烈波动。来源：各厂商 2024 年度财报；SemiAnalysis GPU 产能追踪

根因一：通信墙--GPU 在等数据，不在算

大模型训练采用 3D 并行（DP+TP+PP）。每次前向/反向传播后，梯度需在数百个节点间 AllReduce 同步。8192 卡规模下，单次 AllReduce 通信延迟可达数十毫秒。

更深层的问题：算力增速远超互联带宽增速。H100 相比 A100 算力提升约 3 倍，但 InfiniBand 带宽仅 2 倍，NVLink 仅 1.5 倍。

根因二：存储 I/O 瓶颈--Checkpoint 期间的集体停摆

千卡训练每 30-60 分钟保存一次 Checkpoint。Llama-3 405B 单次 Checkpoint 含权重+Adam 优化器状态+梯度，FP16 下约 5.6TB，含副本可达 16TB，若写入带宽 50GB/s，耗时超 5 分钟。此期间全部 GPU 空闲等待--直接吃掉 5-10% 有效训练时间。频繁故障恢复场景下，损耗可累积至 15%+。

根因三：内存墙--推理场景的带宽浪费

LLM 推理的 Decode 阶段是典型的内存带宽受限任务：每生成一个 Token，需要将整个模型权重 + KV Cache 从 HBM 读入 SM 计算一次，实际 FLOPs 极少。H100 FP16 峰值 1979 TFLOPS，但 Decode 阶段实际算力利用率可能不到 5%。

根因四 & 五：调度粗放 + 供需错配

调度粗放：多数集群仍以「整卡」为最小调度单元。推理任务负载潮汐效应明显，缺乏细粒度弹性（MIG/MPS）导致低谷期大量 GPU 闲置却无法释放。

供需错配：厂商基于「峰值需求」建设集群，训练集群和推理集群物理隔离。训练完成后 GPU 闲置，推理扩容时又无卡可用。白天高峰 GPU 满载、夜间低谷闲置 60-70%。

反直觉洞察：增加 GPU 反而可能降低集群有效算力。通信开销随节点数非线性增长--从 1024 卡扩展到 8192 卡，单卡有效算力可能下降 15-20%。这意味着存在一个「规模收益递减拐点」，越过之后买更多卡只会让问题更严重。在算力增速 > 互联增速的前提下，「堆卡」是最昂贵的低效方案。

规模收益递减拐点：量化分析

「堆卡降效」并非直觉错觉，而是一个可量化的工程规律。集群有效算力随 GPU 数量的增长可用以下模型估算：

集群有效算力估算：
Effective_FLOPS = N × Peak_FLOPS × MFU(N)
其中 MFU(N) 随 N 衰减：

MFU(N) ≈ MFU₀ × (1 - α × log₂(N/N₀))

N₀ = 基准规模（如 512 卡），MFU₀ = 基准 MFU
α = 通信衰减系数（典型值 0.03-0.06，取决于网络拓扑和并行策略）

示例（α=0.05, MFU₀=45% @ 512 卡）：
• N=1024: MFU ≈ 45% × 0.965 = 43.4%
• N=4096: MFU ≈ 45% × 0.890 = 40.1%
• N=8192: MFU ≈ 45% × 0.855 = 38.5%
• N=16384: MFU ≈ 45% × 0.820 = 36.9%

从 512 卡到 16384 卡（32 倍），有效算力仅增长约 26 倍（而非 32 倍），损耗约 18%。α 越大（网络越弱），拐点来得越早。

一句话解释：卡越多，通信开销越大，单卡效率越低。网络越差，这个拐点来得越早--这就是为什么「堆卡」不能无限扩容。

关键判断：拐点位置取决于 α。当 α > 0.08（如使用旧版网络或 MoE All-to-All 密集场景），512 卡以上就开始显著衰减。这也是为什么 RDMA 网络 + 拓扑感知调度对大规模集群至关重要的量化依据。来源：基于 Megatron-LM 通信模型的估算；α 参数校准自 Meta Llama-3 训练日志

如果资源有限、只能优先解决一个问题，应该先解决哪个？以下按投入产出比排序：

优先级根因投入产出比理由

3D 并行：三种并行维度的通信拓扑

大模型训练无法放入单卡显存（70B 模型 FP16 权重 140GB，远超 H100 的 80GB HBM），必须将模型切分到多卡上。3D 并行是当前工业界标准方案，将三种切分维度叠加：

并行维度切分对象通信模式通信频率典型部署
TP（张量并行）模型权重矩阵AllReduce（每层 2 次）极高（每层前后）节点内 8 卡（NVLink）
PP（流水线并行）模型层（Stage）P2P（激活值传递）中（每个 Stage 边界）跨节点（InfiniBand）
DP（数据并行）训练数据 BatchAllReduce（梯度同步）低（每步 1 次）跨节点组（InfiniBand）

组合原则：TP 放在节点内（利用 NVLink 900GB/s 带宽，减少 AllReduce 延迟）；PP 跨节点（激活值较小，P2P 通信量可控）；DP 跨节点组（梯度 AllReduce 可与下一轮前向计算重叠）。

关键矛盾：TP 的 AllReduce 每层执行 2 次，通信频率极高，必须依赖 NVLink 带宽。一旦 TP 跨节点（走 InfiniBand），通信延迟将急剧上升。这就是为什么 TP=8（节点内 8 卡）几乎是不成文的行业标准。

来源：Megatron-LM 论文 (NVIDIA, 2022)；DeepSpeed 论文 (Microsoft, 2020-2023)
通俗类比：把 3D 并行想象成一条三层高速公路系统--
• TP（张量并行）= 车道分割：同一段路分成 8 条车道（NVLink 域内 8 卡），车流同步行驶，每到一个路口（模型层）要对齐一次。车道越多同步越频繁，所以必须修在同一地段内（NVLink）。
• PP（流水线并行）= 收费站接力：路分成若干段（Stage），每段终点把货物（激活值）交给下一段。交接有时间差（气泡），但货物不大（P2P 通信量小）。
• DP（数据并行）= 多条平行高速：每条路跑不同的货（不同 Batch），跑完后在枢纽站汇总对账（AllReduce 梯度同步），对完账再一起发下一批。

三层叠加：车道内同步（TP）-> 段间接力（PP）-> 路间对账（DP）。修路成本最高的是车道同步，所以车道（TP）只修在 NVLink 域内。

3D 并行通信拓扑可视化

3D 并行拓扑：TP 在节点内通过 NVLink 通信（频率最高）；PP 在流水线相邻 Stage 间通过 IB 传递激活值；DP 在同 Stage 的节点组间通过 IB 做 AllReduce 梯度同步

流水线气泡：PP 的隐性代价

流水线并行引入了一个独特的效率损耗：Pipeline Bubble（流水线气泡）。当 PP Stage 0 在执行前向传播时，Stage 1 必须等待 Stage 0 的激活值到达后才能开始计算。这种等待产生了「气泡」--GPU 空闲的时间窗口。

气泡占比估算：
Bubble Ratio ≈ (PP - 1) / (M + PP - 1)
PP = 流水线阶段数，M = Micro-batch 数量

示例：PP=8, M=16 -> Bubble = 7/23 ≈ 30%
示例：PP=4, M=64 -> Bubble = 3/67 ≈ 4.5%
结论：增加 Micro-batch 数量 M 可有效稀释气泡。但 M 受限于显存（每个 Micro-batch 需存储激活值）。

1F1B（One Forward One Backward）调度和 Interleaved PP（交错流水线）是两种主流的气泡消减策略，可将气泡从 O(PP/M) 降至 O(PP/(M×K))，K 为交错因子。来源：Megatron-LM PipeDream-Flush 论文 (NVIDIA, 2021)

MoE Expert Parallelism：All-to-All 通信的新瓶颈

MoE（Mixture of Experts，混合专家模型）是 2024-2026 年最重要的模型架构趋势。DeepSeek-V3（671B 参数，37B 激活）、Mixtral 8×22B 均采用 MoE。其核心思想：每个 Token 只激活 Top-K 个专家（通常 K=2-8），而非全部参数，实现「参数量大但计算量小」。

Expert Parallelism（EP）将不同专家分布到不同 GPU 上。这引入了一种全新的通信模式--All-to-All：

输入 Token
分布在各 GPU -> Router/Gate
Top-K 路由决策 -> All-to-All
Token 发往目标 Expert GPU -> Expert 计算
各 GPU 处理收到的 Token -> All-to-All
结果返回原 GPU -> 输出聚合

为什么 All-to-All 是新瓶颈：不同于 AllReduce（有成熟的环状优化算法），All-to-All 是任意到任意的通信模式--每个 GPU 都要向其他所有 GPU 发送和接收不同大小的 Token 批次。在 64+ GPU 规模下，All-to-All 的通信延迟可占总训练时间的 15-25%。

DeepSeek-V3 的创新：采用「1 个共享专家 + 256 个路由专家」设计。共享专家始终激活（处理通用特征），路由专家处理专有特征。部分路由专家采用 EP 分布，而共享专家无需 All-to-All，降低了通信压力。来源：DeepSeek-V3 Technical Report (2024)；Mixtral 论文 (Mistral AI, 2024)

MoE Expert 路由可视化

MoE Expert 路由全流程：Token 经 Router 分配到目标 Expert GPU（第一次 All-to-All），Expert 计算完成后结果返回原 GPU（第二次 All-to-All）

容错与弹性训练：万卡规模的日常故障

容错技术栈：

  • 异步 Checkpoint：将 Checkpoint 写入与训练计算重叠，避免 GPU 等待。PyTorch 的 distributed checkpoint API 支持并行写入。
  • 冗余 Worker（Standby）：预留 5-10% 的 GPU 作为热备，故障时秒级替换。
  • 弹性训练（Elastic Training）：允许训练任务在 GPU 数量变化时动态调整 Batch Size 和并行度，无需重启。Kubernetes + PyTorch Elastic 已支持此能力。
  • 快速恢复：从 Checkpoint 恢复的时间目标 < 5 分钟。关键路径：加载模型权重 -> 重建优化器状态 -> 恢复数据加载器位置。
来源：Meta Llama-3 Cluster Operations Blog (2024)；PyTorch Elastic 文档

网络拓扑设计：Fat-Tree 与 Rail-Optimized

万卡集群的网络拓扑直接决定了通信性能。当前主流方案：

Fat-Tree（胖树拓扑）

• 多层交换机树状结构
• 无阻塞（1:1 oversubscription）
• 任意两节点间等延迟
• 缺点：交换机数量随规模 O(N log N) 增长，线缆成本极高
• 适合：< 4K GPU 规模

Rail-Optimized（轨道优化）

• 每个节点的 8 张 GPU 分别连到 8 条独立 Rail
• 同 Rail 上的 GPU 属于不同节点
• TP 通信走 NVLink（节点内），DP 通信走 Rail（跨节点）
• 优势：减少跨 Rail 流量，适合大规模 TP+DP 混合
• 适合：> 4K GPU 规模

NVIDIA 的 Quantum-2 InfiniBand 交换机（64 端口 400Gbps）是当前标杆。OCS（Optical Circuit Switching，光路交换）是下一代方向--可以动态重构拓扑，在不同训练阶段切换 TP/DP 通信路径。

长上下文训练：Ring Attention 与 Sequence Parallelism

当上下文长度从 4K 扩展到 1M+（如 Gemini 1.5 Pro），单卡无法容纳完整序列的 KV Cache 和激活值。两种关键方案：

Ring Attention将长序列切分到多个 GPU 上，每个 GPU 计算本地 Attention 的同时，通过环形通信将 KV Cache 传递给下一个 GPU。计算与通信重叠，实现线性扩展上下文长度。理论上 N 个 GPU 可处理 N 倍长度的序列。

Sequence Parallelism (SP)将序列维度切分到多个 GPU 上。与 TP（切分 Head 维度）正交，可组合使用。Megatron-LM 的 SP 将 LayerNorm 和 Dropout 的计算从 TP 组中解放出来，减少 TP 组的通信量。

来源：Ring Attention 论文 (UC Berkeley, 2023)；Megatron-LM Sequence Parallelism (NVIDIA, 2022)
训练侧小结：训练 Infra 的核心挑战是「通信开销随规模非线性增长」。3D 并行的三种通信模式（TP AllReduce / PP P2P / DP AllReduce）叠加 MoE 的 All-to-All，构成了一个复杂的通信拓扑优化问题。没有「最优配置」--只有针对特定模型规模、集群规模和互联带宽的「最优组合」。

从 Ch4 开始，我们转向推理侧--这里的矛盾不再是「如何切分模型」，而是「如何让 GPU 不闲着」。
挖掘 GPU 算力基线
不增加一毛钱硬件，纯靠软件把单卡吞吐提升 5-10 倍的六重优化

算力基线的本质：从「峰值算力」到「有效吞吐」

GPU 理论峰值算力（H100 的 1979 TFLOPS）是「纸面算力」。真正决定业务成本的是有效吞吐--单位时间内实际完成的 Token 生成量。提升有效吞吐的关键不在于堆算力，而在于消除 GPU 等待。

在 LLM 推理中，KV Cache（Key-Value Cache，注意力层的键值缓存）是连接「算力」和「带宽」的枢纽。如何管理 KV Cache，直接决定 GPU 能否持续高效运转。

前置知识：注意力变体与 KV Cache 大小

不同注意力机制直接影响 KV Cache 的大小和推理效率，是理解后续优化的前提：

注意力变体代表模型KV Cache 压缩原理
MHA（标准多头注意力）GPT-3, Llama-1/21x（基线）每个 Head 独立存储 K/V
GQA（分组查询注意力）Llama-3, Mistral~4-8x 压缩多个 Query Head 共享一组 K/V Head
MLA（多头潜注意力）DeepSeek-V2/V3/V4~20-50x 压缩将 K/V 压缩到低维潜空间，推理时仅缓存潜向量
SWA（滑窗注意力）Mistral-7B, Gemma固定窗口仅缓存最近 N 个 Token 的 KV，超窗即丢弃

DeepSeek 的 MLA 是当前最激进的 KV Cache 压缩方案：一个 671B 的 MoE 模型，MLA 使单 Token 的 KV Cache 仅为同规模 MHA 模型的约 1/20--1/50。这从模型架构层面大幅缓解了内存墙。来源：DeepSeek-V2 论文 (2024)

KV Cache：原理与核心矛盾

Transformer 自回归生成要求：每生成一个新 Token，需访问之前所有 Token 的 Key/Value 向量。KV Cache 将已计算的 K/V 张量缓存在 HBM 中，将时间复杂度从 O(n²) 降为 O(n)，代价是显存占用随序列长度线性增长。

KV Cache 显存估算（以 Llama-3 70B 为例）：
= 2 × n_layers × n_kv_heads × d_head × seq_len × batch × dtype_bytes
= 2 × 80 × 8 × 128 × 4096 × 1 × 2 (FP16)
≈ 1.3 GB / 请求（4K 上下文）
batch=32 时 ≈ 42 GB，占满一张 H100 的 80GB 显存的 52%

一句话解释：每个用户请求要吃掉 1.3GB 显存来存历史对话，32 个并发用户就吃掉一半显存--这就是为什么 KV Cache 管理是推理效率的第一杠杆。

核心矛盾：Decode 阶段每生成一个 Token，需把整个 KV Cache + 模型权重全部从 HBM 读一遍。实际计算量极小，但数据搬运量巨大--GPU「忙」（HBM 带宽拉满）但「闲」（SM 利用率极低）。

PagedAttention vs RadixAttention：两大 KV Cache 管理范式

PagedAttention (vLLM)

• 借鉴 OS 虚拟内存分页机制
• 固定大小 Block（16 Token/Block）
• 按需分配，按表寻址
• 显存利用率：20-40% -> 90%+
• 缺点：Block 对齐导致内部碎片

RadixAttention (SGLang)

• 基数树管理 KV Cache
• 变长 Key，无内部碎片
• 自动发现最长公共前缀并复用
• 支持 LRU + LFU 双重淘汰
• 优势：无需配置，自动优化

RadixAttention 前缀复用示例: Root ├── [System Prompt] ← 多轮对话共享，命中即复用 │ ├── [User Msg A + AI Reply A] ← 第二轮复用第一轮 │ │ └── [User Msg B + AI Reply B] ← 第三轮复用前两轮 │ └── [User Msg C + AI Reply C] ← 另一对话分支 └── [Document Context] ← RAG 场景共享文档前缀 └── [Query 1] / [Query 2] ← 多个查询复用同一文档

Zero-Overhead Scheduler：消灭 CPU-GPU 串行空泡

传统推理引擎的执行模式是串行的：CPU 准备 Batch -> GPU 执行 -> CPU 准备下一个 Batch -> GPU 执行。CPU 准备期间 GPU 空闲等待。

SGLang 的 Zero-Overhead Scheduler（零开销调度器）实现CPU/GPU 执行重叠：GPU 处理当前 Batch 时，CPU 异步准备下一个 Batch。配合 Continuous Batching（持续批处理，新请求在槽位释放时立即插入），维持高并发填充率。

传统串行模式
CPU 准备->GPU 执行✗CPU 准备->GPU 执行
SGLang 重叠模式
GPU 执行 Batch N⟷CPU 准备 Batch N+1->GPU 执行 Batch N+1

实测在持续负载下可达 95%+ GPU 利用率。

KV Cache 压缩：让有限显存放更多上下文

量化压缩FP16 -> INT8/INT4。INT8 几乎无损，INT4 部分场景可接受。等效提升 2-4 倍并发能力。

稀疏化淘汰注意力分数天然稀疏。H2O、StreamingLLM 只保留 Top-K 重要 KV 条目，超长上下文（128K+）压缩 4-8 倍。

层级存储InfiniGen / CacheGen 将不活跃 KV Cache 卸载到 CPU 内存/SSD，按需换入 HBM，长文本场景 HBM 占用降低 60%+。

Mooncake 解耦Kimi/Moonshot 的 KVCache 解耦传输框架。RDMA P2P 权重同步从 53 秒降至 7.2 秒（7.37x）。多轮对话缓存命中率 >90%。来源：Mooncake 论文 (Kimi/Moonshot, 2024)

小结：KV Cache 管理是挖掘 GPU 算力基线的第一杠杆。MLA 从模型架构层面压缩缓存、RadixAttention 解决「复用」、PagedAttention 解决「碎片」、量化压缩解决「容量」、Continuous Batching 解决「空泡」、Zero-Overhead Scheduler 解决「串行等待」--六者叠加，可将单卡有效吞吐提升 5-10 倍。不增加硬件投入，纯粹靠软件工程把「等待」转化为「计算」。

KV Cache 解决了「单卡效率」问题，但不同推理阶段（Prefill vs Decode）的资源需求差异仍被混在一起。下一章的 PD 分离架构将解决这一维度。
PD 分离架构
让计算密集的 Prefill 和带宽密集的 Decode 各归其位--但有临界点，不是万能药

什么是 PD 分离

PD 分离（Prefill-Decode Disaggregation，预填充-解码解耦）是 LLM 推理服务领域的关键架构创新。它将一次推理请求拆分为两个阶段，分别部署到不同的 GPU 资源池执行：

Prefill（预填充）阶段

• 一次性并行处理完整 Prompt
• 计算 KV Cache
• 计算密集型（Compute-Bound）
• 大矩阵乘法，SM 满载
• 理想硬件：高算力 GPU

Decode（解码）阶段

• 基于 KV Cache 逐 Token 生成
• 每步一次矩阵向量乘
• 内存带宽密集型（Memory-Bound）
• SM 利用率极低（<10%）
• 理想硬件：高带宽 GPU

核心矛盾：两种阶段资源需求截然相反。混跑在同一 GPU 上会产生严重干扰。注：PD 分离是推理侧架构技术，训练场景中 Prefill 概念不同（指前向传播），两者不要混淆。

PD 分离部署拓扑

PD 分离部署拓扑：用户请求经 Router 路由到 Prefill 集群计算 KV Cache，再通过 RDMA 传输到 Decode 集群逐 Token 生成

挑战与代价

  • KV Cache 传输开销：70B 模型、4K 上下文 KV Cache 约 1.3GB（GQA 后），RDMA 传输需数毫秒至数十毫秒。
  • 系统复杂度：需引入 KV Cache Router 跨节点路由，负载均衡、故障转移、一致性管理复杂度显著上升。
  • 流量预测难度：Prefill/Decode 资源配比依赖流量模式精确预测。预测失误反而加剧「又忙又闲」。
  • 非万能方案：小负载或调参不当可导致 20-30% 性能下降。KV Cache 兼容性必须跨 Worker 匹配。

二阶效应：PD 分离的收益-成本 tradeoff 曲线

PD 分离并非「永远有利」。其净收益取决于TTFT 收益（消除 Prefill/Decode 干扰）与KV Cache 传输成本（跨节点 RDMA 传输）的差值。当传输成本超过干扰消除收益时，PD 分离反而降低性能。

PD 分离净收益估算：
Net_Benefit = TTFT_Gain - KV_Transfer_Cost

TTFT_Gain ∝ Batch_Size × Prefill_Time_Saved（随并发增大而增大）
KV_Transfer_Cost ∝ KV_Size / RDMA_Bandwidth（固定开销，与并发无关）

临界点：当 Batch_Size < Threshold 时，Net_Benefit < 0，PD 分离不划算
Threshold ≈ KV_Size × RDMA_Latency / (Prefill_Time_Saved × Token_Gen_Rate)

典型值：70B 模型、4K 上下文，KV Cache ≈ 1.3GB，RDMA 400Gbps 传输 ≈ 26ms
当 Batch > 8 时 TTFT 收益显著超过传输成本；Batch < 4 时 PD 分离可能反而降低性能。

一句话解释：并发越高，PD 分离越划算；并发太低，传 KV Cache 的路费比省下来的时间还贵。

PD 分离 tradeoff 曲线：两条线的交叉点（Batch ≈ 8）是部署决策的临界点。左侧保持混部，右侧切换 PD 分离

实践指导：高并发场景（Batch > 8）部署 PD 分离；低并发原型环境保持混部。流量预测器需要实时监控 Batch Size，在临界点附近动态切换部署模式。这是 NVIDIA Dynamo Router 的核心设计逻辑。来源：DistServe 论文 (UCSD, 2024)；NVIDIA Dynamo 技术文档

洞察：PD 分离的本质是「用架构解耦换资源效率」。它承认 Prefill 和 Decode 在资源需求上的根本差异，不再强求一个 GPU 同时做好两件事。这与云计算早期的「计算与存储分离」异曲同工。

PD 分离解决了「架构维度」的效率问题。下一章转向「计算本身」的效率--如何让每一次矩阵乘法用更少的比特，让每一个时间步生成更多的 Token。
低精度计算与投机采样
两条正交路径：FP8 让每个比特做更多事，投机采样让每个时间步生成更多 Token
本章定位：低精度计算和投机采样是两条相互独立的优化路径。前者优化「每个比特做多少事」（空间维度），后者优化「每个时间步生成多少 Token」（时间维度）。两者可以正交叠加使用。

低精度计算：用更少的比特完成同样的计算

将模型权重和激活值从 FP32/FP16 压缩到 FP8/INT8/INT4/FP4，在可接受的精度损失内换取算力吞吐和显存容量成倍提升。NVIDIA Hopper 架构原生支持 FP8 张量核心，Blackwell（B200/GB200）进一步支持 FP4。

投机采样：用小模型跑在前，大模型批量验

LLM Decode 阶段严格自回归--每次只生成一个 Token。投机采样（Speculative Decoding）的思路：用轻量 Draft 模型快速「猜」出若干候选 Token，再用大模型一次性并行验证全部候选。验证多个 Token 和验证一个 Token 的计算量相同。

关于输出质量：标准 Speculative Decoding 基于 rejection sampling 确保输出分布与大模型完全一致，理论无损。但实际部署中，若 Draft 模型与大模型分布差异过大或精度不同，极端长序列下可能出现微小偏移。来源：Leviathan et al. (Google, 2023)

两项技术的协同效应

低精度计算和投机采样是正交优化路径，可叠加使用。

端到端加速估算（非简单乘法）：
• 低精度（FP8）: ~2x 计算吞吐提升
• 投机采样（EAGLE-2）: ~2-3x Token 生成加速
• 理论乘积: 2 × 2.5 = 5x
• 实际端到端: 3-4x（考虑 Draft 模型开销、KV Cache 传输、调度 overhead）

一句话解释：两项优化理论上能乘出 5 倍加速，但实际有各种杂费（Draft 模型跑也要时间、KV Cache 搬运也要带宽），落地后稳定在 3-4 倍。

设计哲学：「不精确但够用」比「精确但浪费」更优。LLM 本身是概率系统，在可接受精度损失内换取成倍效率提升几乎总是值得的。这是 AI Infra 区别于传统 HPC 的核心思维差异。

AI Infra 的三层价值

第一层：省钱

GPU 利用率从 35% 提升到 70%，等效算力翻倍--省下数十亿美元

第二层：赚钱

更低推理成本 -> 更低 API 价格 -> 更大应用市场 -> 正向飞轮

第三层：定义格局

AI Infra 能力将决定谁能在 AGI 竞赛中笑到最后。模型算法可以被复制，但一个高效运转的十万卡集群--及其背后的工程 know-how--是无法在短期内复制的系统性壁垒。Infra 不是后勤，而是主战场。

终局设想：AI Infra 的终极目标不是建更大的集群，而是让算力像水电一样「即开即用、按量计费、无处不在」。当 MaaS 平台足够成熟时，用户感知不到 GPU 的存在--就像我们用手机时不会关心基站和光纤一样。

但在到达终局之前，行业必须先解决核心矛盾：用一半的 GPU 利用率撑起 10 倍的算力需求增长。这不是靠买更多卡能解决的--它要求 AI Infra 在训练并行、通信、存储、内存、调度、精度、架构每个维度上持续突破。这是一场没有终点的工程马拉松。
